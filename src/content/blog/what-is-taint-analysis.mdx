**Taint analysis is a static program-analysis technique that tracks untrusted data from a source to a security-sensitive sink.** The analyzer follows the value through the program. If that value can reach a sink without passing through an appropriate sanitizer or validation step, the analyzer reports the flow for review.

“Taint checking,” “taint tracking,” and “taint flow analysis” usually describe this same source-to-sink model. In application security, the goal is to find exploitable data paths rather than merely matching dangerous function names.

## How taint analysis works

A useful taint model defines four kinds of program behavior:

1. **Sources** introduce untrusted values, such as HTTP parameters, request bodies, headers, environment variables, files, or database values.
2. **Propagators** move taint through assignments, return values, parameters, object fields, collections, framework APIs, and storage.
3. **Sanitizers** make a value safe for a specific use, such as parameterizing a SQL query or encoding text for an HTML context.
4. **Sinks** are security-sensitive operations, such as executing a command, building a query, rendering HTML, evaluating code, or making a network request.

A source-to-sink path is not automatically a vulnerability. The sanitizer must match the sink: HTML encoding does not make a value safe for a shell command, for example. Good taint analysis preserves enough context to distinguish a protected path from an exploitable one.

## A small taint-flow example

Consider a web controller that reads a request parameter and passes it through a service before using it in a database query. A syntax matcher looking only at the query may see a dangerous API but cannot determine where the string came from. Inter-procedural taint analysis connects the request source, the service call, and the query sink into one trace. If the query uses parameters correctly, a sanitizer model can stop the flow; if it concatenates the request value, the complete path becomes a finding.

## Analysis depth determines what a tool can find

“Supports taint analysis” can mean very different things. The practical difference between taint analysis tools is how much real application structure they can follow without losing the value.

| Analysis depth | What it follows | Typical limit |
| --- | --- | --- |
| Pattern matching | Source and sink in matching syntax | Loses values after an assignment or helper call |
| Local taint analysis | Values within one function | Stops at method boundaries |
| Inter-procedural analysis | Calls and returns across methods | May lose object or framework state |
| Field- and context-sensitive analysis | Objects, fields, call targets, and framework behavior | Requires a resolved program model |
| Cross-endpoint analysis | Values written by one request and read by another | Requires persistence models |

Deeper SAST is useful when the vulnerability lives in ordinary application structure: helper methods, dependency injection, builders, asynchronous work, or persistence. It also raises the importance of precise rules and library models, because more reach without more context can create false alarms.

## What vulnerabilities can taint analysis find?

Taint analysis is a strong fit for vulnerability classes defined by untrusted data reaching a security-sensitive operation. Common examples include:

- SQL, command, template, and code injection;
- cross-site scripting (XSS);
- server-side request forgery (SSRF);
- path traversal and unsafe file access;
- unsafe deserialization; and
- sensitive data reaching logs or external systems.

The same model helps during a security review: once a reviewer identifies an application-specific source, sink, sanitizer, or dangerous dependency behavior, it can be encoded as a rule and checked across the codebase. A finding should include a reviewable source-to-sink path, not only the line containing the sink.

## From security review to CI/CD vulnerability gate

A one-time review finds what exists today. A CI/CD security gate prevents the same vulnerability pattern from returning tomorrow. The useful handoff is a versioned, testable rule rather than a prose-only conclusion.

OpenTaint can run its built-in rules without an AI agent. When an agent is used, its job is to review application-specific context and turn what it learns into explicit taint rules and dependency models. The engine then applies those artifacts with deterministic program analysis on every scan. This keeps flexible reasoning in the review stage and repeatable vulnerability checks in pull requests and CI/CD.

For developers, the same engine runs locally and in CI, produces a complete data-flow trace, and exports SARIF for code-review tooling. A useful gate should be fast enough for ordinary development, reproducible between runs, and narrow enough to block on actionable findings rather than generic warnings.

## Analysis for Java, Kotlin, and Spring

OpenTaint currently analyzes Java and Kotlin build artifacts, with deep modeling for Spring. JVM applications need more than source-file matching: inheritance, generics, virtual dispatch, bytecode dependencies, and dependency injection all affect which code actually runs. OpenTaint resolves those relationships and traces values across methods, fields, asynchronous boundaries, and JPA persistence.

Python, Go, C#, JavaScript, and TypeScript are on the roadmap and are not yet supported. The source-to-sink concepts in this guide are language-independent; the current OpenTaint engine is specialized for Java, Kotlin, and Spring codebases. See the [Spring taint-analysis walkthrough](/blog/spring-analyzer/) for concrete cross-class and stored-flow examples.

## How to evaluate taint analysis tools

Before adopting a tool, test it against code that resembles your application. Check whether it can:

- trace across methods, classes, fields, and the frameworks you use;
- model sanitizers for the correct security context;
- show a complete, reviewable source-to-sink path;
- let your team add or refine sources, sinks, and dependency behavior;
- run locally and on private code with licensing and CI behavior that fit your workflow;
- export findings into the code-review tools developers already use; and
- reproduce the same finding on later scans.

For a worked comparison of analysis depth, read [Semgrep vs. CodeQL vs. OpenTaint](/blog/semgrep-vs-codeql-vs-opentaint/). It tests the same vulnerability as the value moves through progressively harder program structures.

## Taint analysis FAQ

### What is taint analysis?

Taint analysis is a static program-analysis technique that tracks untrusted data from sources, through program operations, to security-sensitive sinks. It reports a path when the data reaches a sink without a valid sanitizer.

### What is a taint flow?

A taint flow is the path an untrusted value takes from a source to a sink. The path can cross variables, methods, objects, framework calls, asynchronous tasks, and storage before it reaches the dangerous operation.

### What vulnerabilities can taint analysis detect?

Taint analysis is commonly used for SQL injection, command injection, cross-site scripting, server-side request forgery, path traversal, unsafe deserialization, template injection, and other vulnerabilities where untrusted data reaches a dangerous API.

### Which languages does OpenTaint support?

OpenTaint currently supports Java and Kotlin, with deep analysis for Spring. Python, Go, C#, JavaScript, and TypeScript are on the roadmap and are not yet available.
