As a tool for finding bugs, SAST is dead, and few people in security would argue otherwise. Hand a codebase to an AI agent today and it reads the code the way a seasoned reviewer would, chases a hunch across a dozen files, and, when it finds something, writes the exploit to prove the bug is real. Pattern-matching SAST can't keep up with that: it keeps trading false positives for false negatives, and no amount of rule tuning gets it out of that trade-off. Even deep dataflow SAST misses bugs when its rules don't cover them. We saw this on [Conductor](/blog/conductor-rce-cve-2026-58138/), where CodeQL, Semgrep OSS, Semgrep Pro, and our own stock rules produced 44 findings between them, and not one of them was the unauthenticated RCE, because none of the stock rule sets treated the GraalVM script evaluator as a dangerous sink. Our agent found the bug and wrote the missing rule.

<ConductorPath />

So if the question is which tool finds the most bugs, the agent wins, and it isn't close. A defender, however, has to answer a different and much harder question: is an entire class of bugs absent from the code?

## Finding bugs isn't proving they're gone

Anthropic recently published [research on making formal verification practical with LLMs](https://www.anthropic.com/research/formal-verification), and it opens with a line that sums up the problem well:

> "Most software is riddled with bugs, which AI can now easily find and exploit. The standard defenses against cyberattacks are no longer sufficient: we need ways to prove that code is free of bugs."

The logic is uncomfortable but simple. Attackers have the same agents you do, so finding bugs faster doesn't protect you on its own: you have to find every bug, while the attacker needs only the one you missed. What you want instead is a statement like "no request parameter in this codebase ever reaches a file-system call," backed by stronger evidence than "an agent looked and didn't find anything."

Formal verification can give you exactly that kind of statement. For decades it has been too expensive for most real projects, and the research argues that AI is finally bringing the price down. We like where this is heading, but it raises two questions. What does a proof actually cost today? And is there already a cheaper tool that covers many of the properties defenders care about?

[@ccrisccris](https://x.com/ccrisccris/status/2114210057105645679) has already suggested an answer to the second one:

> "Part of formal verification can be replaced by more efficient static analysis, and part of static analysis by better programming language design."

We agree. The rest of this post puts numbers on the first half of that quote and then explains why the cheaper tool still deserves to be called a proof.

## What a proof costs

We ran OpenTaint, our static taint analyzer, on a mid-sized Java project of about 100K lines of code and 0.65 MB of bytecode. We checked exactly the kind of property from the example above, namely that no request data reaches a file-system call, which is to say that the code has no path-traversal flows. OpenTaint finished in about a minute of CPU time, without spending a single API token.

Then we asked what it would take to prove the same property with AI and a general-purpose formal verifier.

To keep the comparison fair, imagine it done properly. You embed the JVM bytecode into a formal verifier, and AI writes field- and context-sensitive dataflow semantics for every method (path-insensitive, like the analyzer). You then prove those semantics sound, because otherwise you are simply trusting whatever the AI came up with, and only after that do you prove or disprove the security property itself. To be generous, we'll assume the library models and security rules already exist and won't count their cost.

The expensive part is the middle step, since every single method in the project needs its semantics written and proven. On this project, for this one property, the analyzer produced about 440 MB of dataflow summaries and fixpoint data, which gives a rough measure of how much work a proof would have to cover. From that, we estimate that a cold AI-driven verification run would take about 28.5 billion input tokens and 145 million output tokens. At Claude Opus 5.5 API prices, that comes to roughly $11,500.

<details>
<summary>How we got that number, and how much to trust it</summary>

- **Output.** At roughly 3 bytes per token, 440 MB of summaries and fixpoint data comes to about 145M tokens, which is the cost of writing every method's semantics and the intermediate fixpoint state exactly once.
- **Input.** Every piece the model writes needs context around it: the method's bytecode, the summaries of the methods it calls, and the surrounding proof state. At about 200 tokens read for every token written, that adds up to about 28.5B input tokens.
- **Price.** Opus 5.5 charges $4 per million input tokens, $20 per million output tokens, and $0.20 per million cached input tokens. Output comes to about $2,900, and the ~$8,600 for input only holds if almost all of it is served from the prompt cache. Without caching, the input alone would run to about $114,000.

This is a ballpark figure, and it could be off in either direction.

- It could be too high if a model can describe method semantics more compactly than the analyzer's internal format, or if the proof engine does more of the work. But the more work the proof engine takes on, the more it turns into a static analyzer itself.
- It could be too low, because it leaves out failed proof attempts, retries, and the work of proving the semantics sound.

</details>

It also isn't a one-time cost: part of the work has to be redone whenever the code changes, although proofs for unchanged code can be reused.

<CostBars />

The exact figures matter less than the size of the gap. It is about a minute on a CPU against thousands of dollars in tokens, for one property on one mid-sized project, and Anthropic's own write-up points the same way, with proofs that often ran to hundreds of millions of tokens.

That's why, before you rewrite a codebase in another language (the second half of the quote) or pay agents to prove dataflow properties, it's worth trying static taint analysis first.

## Dataflow SAST is lightweight formal verification

How can an analyzer do in a minute what a proof would spend thousands of dollars on? Because it solves a lighter version of the same problem. A formal proof needs three things, a spec, a model of the environment, and the semantics of the program, and a taint analyzer needs the same three:

<ProofMapping />

The first two are inputs, so someone has to write the rules and the models. The third is where all the cost sat in our estimate, and the analyzer computes it on its own, deriving the dataflow semantics of every method and the fixpoint over the whole project without a single token.

That speed comes from approximation, so the analyzer isn't fully sound. Here is exactly what its semantics cover and where they stop:

<AnalysisScope />

A clean scan is therefore a precise statement rather than a blanket one: under these rules, these models, and these semantics, no such flow exists. That is a narrower claim than "the code is secure," and it is the honest one.

Formal verification makes exactly the same kind of claim. Anthropic is upfront about it: their guarantees rest on trusted hardware and OS models, on the proof checker, and on assumptions about how the programs run. A proof is only as strong as its specs and assumptions, whichever tool produces it. Both approaches are bounded by how much of the world you've modeled; the difference is how much it costs to get the answer.

## What dies and what survives

Which brings us back to the title, borrowed from the old phrase "The king is dead, long live the king": the role doesn't die, it passes on. SAST as a bug finder is dead, because agents do that job better and will only keep improving.

SAST as a prover is what survives. A tool that can say "this kind of flow can't happen, given these stated assumptions" does something no agent can, and it does so in minutes, with the same answer every time, on every commit, inside the processes teams already run: CI gates, SARIF reports, and pull-request checks. To keep that role, these tools have to keep getting more sound and keep their assumptions out in the open.

Pattern matchers don't survive this shift. They match syntax rather than data flow, so a clean result from a pattern matcher tells you nothing about where data actually goes.

That leaves the oldest complaint about SAST, which is false positives. From the proof point of view, a false positive is simply a proof that didn't go through, and you fix it the way you'd fix any proof: you adopt coding standards the analyzer understands, and you configure it to match your real security assumptions, such as known sanitizers and safe configurations. Sticking to a coding standard used to cost developers real effort, but when an agent writes much of the code, it costs almost nothing.

This view also means that agents and analyzers no longer compete but complement each other. The two inputs in the mapping above that the analyzer can't compute itself, the rules (which are really formal security specs) and the library models, are exactly the kind of work AI is good at. That's what our [AppSec agent](/blog/appsec-agent/) does: you pay for the model's work once, and from then on the engine re-checks every commit for the cost of CPU time.

## Where to start

Agents are the best bug finders available today, but a list of bugs, however long, is not a guarantee. Pair them with taint analysis: it's still SAST, so it fits into the processes you already run, and it's fast and cheap.
