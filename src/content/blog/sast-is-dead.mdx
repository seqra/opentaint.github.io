As a tool for finding bugs, SAST is dead. Give an AI agent a codebase today, and it can read the code like an experienced reviewer, follow a hunch across a dozen files, and even write an exploit to prove a bug is real. Pattern-matching SAST can't keep up. It's stuck trading false positives for false negatives, and no amount of rule tuning can solve that problem. Even advanced dataflow analysis has its limits: if a bug falls outside what the rules cover, it gets missed.

We saw exactly this with [Conductor](/blog/conductor-rce-cve-2026-58138/). CodeQL, Semgrep, and our own stock rules produced half a hundred findings between them, but not one caught the unauthenticated RCE. The reason was simple: none of the stock rule sets recognized the GraalVM script evaluator as a dangerous sink. Our agent, however, successfully found the vulnerability and wrote the rule needed to detect it.

<ConductorPath />

So if the question is which tool finds the most bugs, the agent wins, and it isn't even close. But defenders face a different, much harder question: how do you know an entire class of bugs is absent from your code?

## Finding bugs isn't proving they're gone

Anthropic recently published [research on making formal verification practical with LLMs](https://www.anthropic.com/research/formal-verification), and it opens with a line that captures the problem well:

> "Most software is riddled with bugs, which AI can now easily find and exploit. The standard defenses against cyberattacks are no longer sufficient: we need ways to prove that code is free of bugs."

The logic is uncomfortable but simple. Attackers have access to the same agents you do, so finding bugs faster isn't enough to keep you safe. You have to find every bug, while an attacker only needs to find the one you missed. What you really want is to be able to say something like "no request parameter in this codebase can ever reach a file-system call," with stronger evidence to back it up than "an agent looked and didn't find anything."

Formal verification can give you exactly that kind of guarantee. For decades, though, it has been too expensive for most real-world projects. Anthropic's research argues that AI is finally bringing the cost down. We like where this is heading, but it leaves us with two questions: how much does a formal proof actually cost today, and is there already a cheaper way to establish some of the properties defenders care about?

[@ccrisccris](https://x.com/ccrisccris/status/2114210057105645679) has already offered an answer to the second question:

> "Part of formal verification can be replaced by more efficient static analysis, and part of static analysis by better programming language design."

We agree. In the rest of this post, we’ll put some speculative numbers on what formal verification costs today, then show how static taint analysis can prove specific properties that matter to defenders at a fraction of the cost.

## What a proof costs

We ran OpenTaint, our static taint analyzer, on a mid-sized Java project with 100K lines of code and 0.65 MB of bytecode. We checked a specific security property: no request-controlled data can reach a dangerous file-system call, or, to be precise, there are no path-traversal flows. OpenTaint finished in about a minute of CPU time, without spending a single API token.

But what would it cost to prove the same property using AI and a general-purpose formal verifier?

To make the comparison fair, let's assume we do it properly. First, we embed the JVM bytecode into a formal verifier. Then we have AI write field- and context-sensitive dataflow semantics for every method, keeping the analysis path-insensitive, just like OpenTaint. We'd also need to prove those semantics are sound. Otherwise, we're just trusting whatever the AI generated. Only then can we prove or disprove the security property itself. We'll also assume the library models and security rules already exist, just as they do for OpenTaint, and leave their cost out of the estimate.

Most of the cost comes from writing the semantics and proving them sound, since every method needs both. For this one property, OpenTaint generated 440 MB of dataflow summaries and fixpoint data. That's not a direct measure of proof complexity, but it gives us a rough idea of how much work is involved. Based on that, we estimate that an AI-driven verification run from scratch would require around 145 million output tokens and 28.5 billion input tokens. At Claude Opus 5.5 API prices, that works out to roughly $11,500.

<details>
<summary>How we got that number, and how much to trust it</summary>

- **Output.** At roughly 3 bytes per token, 440 MB of summaries and fixpoint data works out to about 145 million output tokens. This assumes the model writes every method's semantics and the intermediate fixpoint state exactly once.
- **Input.** For everything the model writes, it needs context: the method's bytecode, summaries of the methods it calls, and the surrounding proof state. At roughly 200 input tokens for every output token, that adds up to about 28.5 billion input tokens.
- **Price.** Opus 5.5 charges $4 per million input tokens, $20 per million output tokens, and $0.20 per million cached input tokens. That's about $2,900 for output and $8,600 for input, assuming roughly 97% of input tokens are served from the prompt cache. Without caching, input alone would cost about $114,000, bringing the total to roughly $117,000.

These are ballpark numbers, and the actual cost could go either way.

- **It could be lower** if the model can express method semantics more compactly than the analyzer's internal format, or if the proof engine handles more of the work. But the more work the proof engine takes on, the closer it gets to being a static analyzer itself.
- **It could be higher** because the estimate doesn't account for failed proof attempts, retries, or the additional work needed to prove the semantics sound.

</details>

And this isn't a one-time cost. Every code change can mean redoing part of the work, although proofs for unchanged code can be reused when their assumptions still hold.

The exact numbers matter less than the gap: a minute of CPU time versus thousands of dollars, for a single property in a single project. So before rewriting your codebase in another language (the second half of the quote) or paying AI agents to prove dataflow properties, it's worth trying static taint analysis first.

## Dataflow SAST is lightweight formal verification

How can an analyzer do in a minute what an AI-driven proof might cost thousands of dollars to do? Because we're asking a much narrower question: whether data can flow from one part of the program to another. By focusing on dataflow properties, we can specialize both the specifications and the way we prove them, rather than building a general-purpose proof from scratch. The underlying ingredients are still the same. A formal proof needs three things: a specification, a model of the environment, and the semantics of the program. A taint analyzer works with the same three.

<ProofMapping />

The first two are inputs: someone has to write the rules and build the models. The third is where most of the cost comes from in our estimate. But instead of having AI write and prove the dataflow semantics method by method, the analyzer computes them itself, along with the fixpoint for the whole project, without spending a single API token.

That speed comes with trade-offs. The analyzer approximates program behavior, and it isn't fully sound: it doesn't handle some language features, including reflection and exceptions. Here's what its analysis covers and where it stops:

<AnalysisScope />

So a clean scan doesn't mean "the code is secure." It means something more specific: under these rules, models, and supported semantics, no such flow exists. That's a narrower claim, but it's still a useful guarantee.

Formal verification also comes with assumptions. Anthropic is upfront about this: its guarantees depend on trusted hardware and OS models, the proof checker, and assumptions about how programs run. Any proof is only as strong as the specifications and assumptions behind it. What matters is knowing exactly what you're proving, what you're leaving out, and how much it costs to get there.

## What dies and what survives

Which brings us back to the title, borrowed from the old phrase "The king is dead, long live the king": the role doesn't die, it passes on. SAST as a bug finder is dead, because agents do that job better and will only keep improving. Pattern matchers don't survive at all: they match syntax rather than data flow, so a clean result from one tells you nothing about where data actually goes.

SAST as a prover is what survives. A tool that can say "this kind of flow can't happen, given these stated assumptions" gives you something a list of findings never will. It does so in minutes, with the same answer every time, on every commit, inside the processes teams already run: CI gates, SARIF reports, and pull-request checks. To keep that role, these tools have to keep getting more sound, and keep their assumptions out in the open.

That leaves the oldest complaint about SAST: false positives. From the proof point of view, a false positive is a proof that didn't go through, and you fix it the way you'd fix any proof. You adopt coding standards the analyzer understands, and you configure it to match your real security assumptions, such as known sanitizers and safe configurations. Sticking to a coding standard used to cost developers real effort. When an agent writes much of the code, it costs almost nothing.

Seen this way, agents and analyzers don't compete. They complement each other. The two inputs the analyzer can't compute for itself, the rules and the library models, are exactly the kind of work AI is good at. The rules are really formal security specs, and our [AppSec agent](/blog/appsec-agent/) writes them the way it wrote the missing Conductor rule. You pay for the model's work once, and from then on the engine re-checks every commit on CPU.
